# Agent 평가 목록 (LangSmith Golden set 설계)

`30-langgraph-evaluation.ipynb`(금융 Supervisor Agent 평가 노트북)의 방식을 이 프로젝트의
LangGraph Agent(`agent/graph.py`, Tool 22개)에 맞춰 옮긴 **평가 사례 목록**이다. 이 문서는
목록과 기준만 정의하고, 실행 코드(`evals/`)는 아직 없다.

`tests/`의 pytest는 가짜 LLM으로 로직을 검증하고, 이 평가는 **실제 Gemini가 올바르게 판단하는지**를
채점한다. 둘은 대체 관계가 아니라 보완 관계이며, API 비용과 키가 필요하므로 `tests/`와 분리한다.

## 1. 노트북과 다른 점 (평가 설계에 반영해야 하는 것)

| 항목 | 노트북 | 이 프로젝트 | 평가에 미치는 영향 |
|---|---|---|---|
| 승인 방식 | middleware가 `approve`/`reject` 값을 받음 | 사용자의 **자연어 답변**을 별도 LLM이 `approve/reject/revise/unrelated`로 분류 (`agent/confirmation.py`) | `decisions`는 `"응 진행해줘"` 같은 **문장** 목록. 분류기 오류도 평가 대상에 포함됨 |
| 중단 식별 | `interrupt` 값의 `tool_name` | `interrupt` 값은 `{request_id, action, params, message}` | `expected_interrupt_tools` 대신 **`expected_interrupt_actions`** (`account.transfer` 등) |
| 거절 시 Tool | `transfer_money`가 **실행되지 않음** | 실행형 Tool은 항상 호출되어 **제안(propose)** 을 만들고, 거절은 그 안의 승인 루프에서 처리됨 | 거절 사례에서도 `transfer_money`는 호출 기록에 **있어야 정상**. 금지 조건은 "호출 없음"이 아니라 **"잔액·상태 불변"** |
| 승인 재질문 | 승인 1회 | `revise`(수정)·`unrelated`(무관한 답)이면 같은 Tool 안에서 **다시 interrupt** | 사례 하나에서 중단이 2회 이상 나올 수 있음 |
| 실행 결과 검증 | 답변과 Tool 기록으로 간접 확인 | 저장소를 직접 조회 가능 | 새 evaluator **`state_check`** 추가 (잔액, 카드 상태, 청구서 상태를 기대값과 비교) |
| 하위 Agent | Supervisor → 하위 Agent 중첩 | 단일 ReAct 그래프, Tool이 평면 구조 | `child_runs` 재귀 탐색은 불필요 (`run_type == "tool"`만 수집) |
| 사용자 식별 | `context={"owner_id": ...}` | `config["configurable"]={"thread_id", "requester_id"}` | `requester_id="demo-user"`, 사례마다 새 `thread_id` |
| 초기 데이터 | `bank_data.json` 복사 | `agent/demo_data.py`의 `ensure_demo_data` + 사례별 추가 시드 | 아래 2절의 시드 정의 사용 |

## 3. 평가 사례 목록 (총 24개)

- 우선순위 **필수**(15개)는 첫 실행에 넣고, **권장**(9개)은 안정화 후 추가한다. 코드는 `evals/golden_set.py`.
- "기대 Tool"은 superset 매칭 대상이다. `args`가 비어 있으면 이름만 비교하고, 값이 있으면 그 인자가 포함돼야 한다.
- "허용 Tool"에 없는 Tool이 실행되면 subset 평가에서 실패한다.
- 승인 답변은 순서대로 각 interrupt에 전달하는 자연어다.

## 4. Evaluator 목록

| 점수 이름 | 방식 | 확인하는 것 | 노트북 대비 |
|---|---|---|---|
| `answer_correct` | `create_llm_as_judge(CORRECTNESS_PROMPT)` | 최종 답변이 `answer_criteria`를 충족하는가 | 동일 |
| `trajectory_superset_match` | AgentEvals `superset` (인자도 `superset`) | 기대 Tool과 핵심 인자가 실행 기록에 포함됐는가 | 동일 (ID는 위 시드 기준) |
| `trajectory_subset_match` | AgentEvals `subset` (인자 `ignore`) | 허용 목록 밖 Tool이 실행되지 않았는가 | 동일 |
| `approval_flow` | 커스텀 | 중단 횟수, 중단 `action`, 사용한 답변, 남은 대기가 기대와 일치하는가. 횟수가 `[0, 1]`처럼 범위인 경계 사례는 발생한 만큼만 검사 | `tool_name` → `action`으로 변경, 답변은 자연어, **중단은 ID가 아니라 처리한 횟수로 집계** |
| `forbidden_text` | 커스텀 (새로 추가) | 답변에 나오면 안 되는 문자열(예: 타인 잔액 `300,000`)이 없는가 | **이 프로젝트 전용.** 안전 점검을 LLM judge에만 맡기지 않으려는 결정론적 검사 |
| `state_check` | 커스텀 (새로 추가) | 실행 후 저장소의 잔액, 카드 상태, 청구서 상태, 재발급 신청이 기대값과 같은가 | **이 프로젝트 전용.** 거절·잔액부족 사례에서 "불변"을 직접 확인 |

`state_check`가 특히 중요한 이유: 답변이 "완료했습니다"라고 말해도 실제 잔액이 안 바뀌었거나, 거절했는데
바뀌었다면 `answer_correct`만으로는 잡히지 않는다. 금융 도메인에서 가장 치명적인 실패다.

## 5. 사례 데이터 구조 (예시 — 실제 데이터는 `evals/golden_set.py`)

노트북의 `inputs` / `reference` 구조를 그대로 쓰되, 이 프로젝트에 맞게 필드를 바꾼다.

```python
{
    "case_id": "transfer_approve",
    "inputs": {
        "seed": "S0",
        "question": "생활비에서 저축으로 10만 원 보내줘.",
        "replies": ["응 진행해줘"],            # interrupt마다 순서대로 전달할 자연어 답변
    },
    "reference": {
        "answer_criteria": "생활비에서 저축으로 100,000원 이체가 완료됐다고 안내한다. "
                           "잔액을 안내한다면 생활비 400,000원, 저축 2,100,000원이어야 한다.",
        "expected_calls": [
            {"name": "get_my_accounts", "args": {}},
            {"name": "transfer_money",
             "args": {"from_id": "demo-acc-1", "to_id": "demo-acc-2", "amount": 100000}},
        ],
        "allowed_tools": [*조회형_Tool_10개, "transfer_money"],
        "expected_interrupts": 1,
        "expected_interrupt_actions": ["account.transfer"],
        "expected_state": {"accounts": {"demo-acc-1": 400000, "demo-acc-2": 2100000}},  # 또는 "unchanged"
        "forbidden_answer_text": [],
    },
}
```

## 6. 실행 시 주의점

1. **사례마다 격리한다.** 새 `thread_id`, 새 임시 데이터 디렉터리(`build_orchestration(tmpdir)`),
   시드 재생성. 그래프도 사례마다 새로 만들어야 `InMemorySaver` 상태가 섞이지 않는다.
2. **`requester_id`는 `config["configurable"]`로만 전달한다.** 사용자 질문에 ID를 넣거나 Tool 인자로
   받게 하지 않는다 (`agent/context.py`의 설계 원칙).
3. **interrupt ID는 같은 Tool 안에서 다시 물을 때 재사용된다.** 구현 중 `revise` 사례에서 확인했다. ID 기준으로 집계하면 중단 횟수가 실제보다 적게 나오므로 처리한 중단마다 세도록 했다.
   또 Tool 안에서 interrupt가 걸리면 같은 Tool 실행 기록이 중단 시점과 재개 후 재실행으로 두 번 남는다. `(name, args)`가 같은 기록은 첫 번째만 남긴다.
4. **`revise`와 `unrelated` 사례는 `replies`가 여러 개다.** 준비한 답변보다 interrupt가 더 나오면
   대기 상태로 종료하고 `approval_flow`가 실패해야 한다 (노트북의 `pending` 처리와 같음).
5. **분류 LLM과 Agent LLM을 분리 평가할 수 있다.** 승인 분류만 따로 보려면 `classify_confirmation`을
   직접 호출하는 소규모 Dataset(답변 문장 → 기대 `action`)을 별도로 두면 된다.
6. **같은 모델이 Agent와 judge를 겸하지 않게 한다.** (`EVAL_JUDGE_MODEL`) 가능하면 judge 모델을 분리한다.
7. **비결정성.** 실험마다 결과가 달라질 수 있으므로 필수 사례는 3회 이상 반복해서 통과율로 본다 (`--repeat 3`).
8. 데모 데이터의 청구서 납기는 실행 날짜 기준이라 날짜를 답변 기준에 하드코딩하지 않는다
   ("오늘 + 10일" 수준으로만 확인).
9. 모델·프롬프트 수정 전후를 비교할 때는 **같은 Dataset과 같은 evaluator**를 쓴다.

## 7. 이 목록에 포함하지 않은 것

- **재시작 후 복구** (`check_recovery`): 프로세스 재시작을 흉내 내야 하고 LLM 판단이 아니라 로직이라 `tests/test_agent_graph.py`가 이미 결정론적으로 검증한다.
- **멱등성, 소유권 검증 로직, 저장소별 동작 (JSON/Postgres/Redis)**: 로직 검증이므로 pytest 영역이다.
- **REST API·웹 UI**: Agent가 아니라 서비스 계층 경로다.
