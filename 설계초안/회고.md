# 회고

## 배운 점

- Spring 프레임워크를 공부하다가 이번 프로젝트는 파이썬으로 하게 됐습니다. 처음엔 익숙한
  대로 Spring 같은 구조로 설계하려고 했는데, 진행하면서 파이썬 환경에는 그것과는 다른, 더
  알맞는 구조가 있다는 걸 배웠습니다. 예를 들어 Java의 `interface`/DI 컨테이너 감각으로
  접근하려다가, 파이썬에서는 `typing.Protocol` + 생성자 주입만으로도 충분하다는 걸 알게
  됐고(구현체에 굳이 `Impl` 접미사를 안 붙이기로 한 것도 이 때문입니다), Enum이나 dataclass
  같은 파이썬다운 도구를 그대로 쓰는 게 오히려 더 명확했습니다.
- 자동화 테스트를 최대한 꼼꼼하게 만들어서 전부 통과시켰는데도, 실제로 돌려보니 테스트
  단계에서는 못 잡았던 오류들이 많이 나왔습니다. 특히 에이전트와의 상호작용은 확률 기반이라,
  실행 중에 잡힌 오류를 다시 테스트로 내려서 재현하려고 해도 같은 오류가 잘 안 잡힌다는 걸
  알게 됐습니다. 그래서 앞으로는 확률에 따른 변동성 자체를 최대한 줄이는 구조로 설계해야겠다고
  생각했습니다.
- "로컬에서 됨"과 "실제 프로덕션에서 됨" 사이의 간극이 생각보다 컸습니다. 브랜치 이름,
  컨테이너 베이스 이미지, 공유 비밀번호의 URL 특수문자 같은 것들은 전부 실제로 배포해봐야만
  드러났습니다.

## 어려웠던 점과 해결 과정

1. **조회 요청조차 응답이 완전히 비어 있었습니다.** 실제 API 키로 처음 돌려봤을 때 "내 계좌
   목록 보여줘" 같은 단순 조회조차 빈 응답이 왔습니다. tool을 1개씩 늘려가며 재현 조건을
   좁혀보니, tool을 15개 이상 bind하면 모델이 `thinking_budget`(기본값 -1, "동적")을 전부
   써버리고 tool 호출도 텍스트도 없이 끝나버리는 걸 확인했습니다. 고정값(1024)으로 바꿔서
   해결했습니다.
2. **이체 요청을 했는데 tool을 안 부르고 채팅으로 먼저 되물었습니다.** 버그인 줄 알았는데,
   시스템 프롬프트가 "tool 자체가 승인을 담당한다"는 걸 명시하지 않아서 모델이 나름대로
   안전하게 행동한 것이었습니다. 별명("생활비")을 ID로 못 바꿔서 계좌를 못 찾겠다고 답하는
   문제도 같이 발견해서, 규칙을 명시하고 few-shot 예시를 넣어 해결했습니다.

## 남은 한계와 개선하고 싶은 점

- 시스템 프롬프트가 아직 100% 안정적이진 않습니다 — 별명으로만 지칭했을 때 가끔 확인 질문을
  먼저 하는 경우가 남아있을 수 있어서, few-shot을 더 늘리거나 아예 파라미터를 구조화된
  형태로 강제하는 방향을 고려해볼 만합니다.
- 계좌/카드/청구서를 "생성"하는 기능 자체가 없어서 데모 데이터에 의존합니다 — 처음부터
  "기존 것을 다루는" 기능만 요구받았기 때문입니다.
- 청구서는 미납만 조회할 수 있고 납부 완료 이력은 따로 조회할 방법이 없습니다 — 필요해지면
  조회 기능을 추가하면 됩니다.
- 카드 재발급 신청 시 배송지(집/회사) 선택 UI는 생략하고 항상 "집"으로 고정해뒀습니다.
