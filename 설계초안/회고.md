# 회고

## 배운 점

- Spring 프레임워크를 공부하다가 이번 프로젝트는 파이썬으로 하게 됐습니다. 처음엔 익숙한
  대로 Spring 같은 구조로 설계하려고 했는데, 진행하면서 파이썬 환경에는 그것과는 다른, 더
  알맞는 구조가 있다는 걸 배웠습니다. 예를 들어 Java의 `interface`/DI 컨테이너 감각으로
  접근하려다가, 파이썬에서는 `typing.Protocol` + 생성자 주입만으로도 충분하다는 걸 알게
  됐고(구현체에 굳이 `Impl` 접미사를 안 붙이기로 한 것도 이 때문입니다), Enum이나 dataclass
  같은 파이썬다운 도구를 그대로 쓰는 게 오히려 더 명확했습니다.
- 계층을 Domain → Repository → Service로 제대로 나눠두니 저장소를 세 번(Memory → JSON →
  Postgres/Redis) 바꾸는 동안 서비스 코드는 한 줄도 안 고쳐도 됐습니다. "나중에 바꾸기 쉽게
  설계하라"는 말을 들을 땐 막연했는데, 실제로 세 번 바꿔보고 나서야 체감했습니다.
- 자동화 테스트가 전부 통과해도 LLM 에이전트는 그것만으로 검증이 안 된다는 것도 배웠습니다.
  실제 Gemini API로 돌려보니 테스트로는 절대 안 잡히는 문제들(아래 참고)이 나왔습니다.
- "로컬에서 됨"과 "실제 프로덕션에서 됨" 사이의 간극이 생각보다 컸습니다. 브랜치 이름,
  컨테이너 베이스 이미지, 공유 비밀번호의 URL 특수문자 같은 것들은 전부 실제로 배포해봐야만
  드러났습니다.

## 어려웠던 점과 해결 과정

1. **조회 요청조차 응답이 완전히 비어 있었습니다.** 실제 API 키로 처음 돌려봤을 때 "내 계좌
   목록 보여줘" 같은 단순 조회조차 빈 응답이 왔습니다. tool을 1개씩 늘려가며 재현 조건을
   좁혀보니, tool을 15개 이상 bind하면 모델이 `thinking_budget`(기본값 -1, "동적")을 전부
   써버리고 tool 호출도 텍스트도 없이 끝나버리는 걸 확인했습니다. 고정값(1024)으로 바꿔서
   해결했습니다.
2. **이체 요청을 했는데 tool을 안 부르고 채팅으로 먼저 되물었습니다.** 버그인 줄 알았는데,
   시스템 프롬프트가 "tool 자체가 승인을 담당한다"는 걸 명시하지 않아서 모델이 나름대로
   안전하게 행동한 것이었습니다. 별명("생활비")을 ID로 못 바꿔서 계좌를 못 찾겠다고 답하는
   문제도 같이 발견해서, 규칙을 명시하고 few-shot 예시를 넣어 해결했습니다.
3. **배포 파이프라인이 아예 실행이 안 됐습니다.** 참고했던 템플릿을 그대로 복사하면서
   브랜치를 `master`로 뒀는데, 이 저장소 기본 브랜치는 `main`이었습니다. 실제로 push해보기
   전까지는 전혀 몰랐던 문제였습니다.
4. **Redis 연결이 `localhost:3`으로 시도되는 황당한 에러가 났습니다.** 공유 Redis 비밀번호에
   `/`, `+`, `=` 같은 URL 특수문자가 들어있었는데, 이걸 URL 인코딩 없이 그대로 접속 문자열에
   넣어서 파서가 host:port를 엉뚱하게 잘랐던 것이었습니다. `urllib.parse.quote()`로 인코딩해서
   해결했습니다.
5. **컨테이너는 떠 있는데 계속 unhealthy 상태였습니다.** 헬스체크가 `wget`을 쓰는데, 정작
   베이스 이미지엔 `wget`이 없었습니다. 파이썬 표준 라이브러리로 헬스체크를 바꿔서
   해결했습니다.
6. **웹 채팅에서 챗봇 답변이 가끔 `[object Object]`로 깨졌습니다.** Gemini가 답변을 일반
   문자열이 아니라 `[{"type": "text", "text": "..."}]` 같은 다중 파트 리스트로 반환할 때가
   있었는데, 이걸 그대로 화면에 넘기다 보니 생긴 문제였습니다. 텍스트 파트만 골라 이어붙이는
   변환 함수를 추가해서 해결했습니다.

## 남은 한계와 개선하고 싶은 점

- 시스템 프롬프트가 아직 100% 안정적이진 않습니다 — 별명으로만 지칭했을 때 가끔 확인 질문을
  먼저 하는 경우가 남아있을 수 있어서, few-shot을 더 늘리거나 아예 파라미터를 구조화된
  형태로 강제하는 방향을 고려해볼 만합니다.
- LangGraph 체크포인터가 `InMemorySaver`(휘발성)라서, 서버가 재시작되면 진행 중이던 "대화
  맥락"은 날아갑니다(승인 대기 자체는 Postgres/Redis에 있어서 안전하지만). 여러 인스턴스로
  수평 확장하려면 `langgraph-checkpoint-postgres` 같은 걸로 바꿔야 합니다.
- 이 환경에 Terraform 바이너리가 없어서 ECR 리소스를 `aws ecr` CLI로 직접 만들었습니다 —
  실제 Terraform state 밖에 있는 상태라, 나중에 `terraform import`로 편입해야 합니다.
- 두 계좌 사이의 반대 방향 동시 이체(A→B, B→A)가 겹치면 `SELECT ... FOR UPDATE` 잠금 순서가
  엇갈려 데드락이 날 이론적 가능성이 있습니다 — 지금 규모에선 Postgres가 자동 감지해 한쪽을
  에러로 중단시키는 것으로 충분하다고 보고 별도 처리는 안 했습니다.
- 계좌/카드/청구서를 "생성"하는 기능 자체가 없어서 데모 데이터에 의존합니다 — 처음부터
  "기존 것을 다루는" 기능만 요구받았기 때문입니다.
- 청구서는 미납만 조회할 수 있고 납부 완료 이력은 따로 조회할 방법이 없습니다 — 필요해지면
  조회 기능을 추가하면 됩니다.
- 카드 재발급 신청 시 배송지(집/회사) 선택 UI는 생략하고 항상 "집"으로 고정해뒀습니다.
- 조건부 이체·분할 이체·카드 재발급·청구서 일괄납부 같은 나머지 실행형 액션은 자동화
  테스트로는 검증됐지만, 실제 Gemini와의 대화로는 아직 확인 안 해봤습니다.
