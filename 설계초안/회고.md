# 회고 (초안 — 본인 목소리로 다듬을 것)

> 이 문서는 Claude가 이번 세션에서 실제로 겪은 문제들을 근거로 초안을 쓴 것. 사실 관계는
> 정확하지만(로그·커밋으로 확인 가능), 느낀 점·강조점은 본인 경험에 맞게 고쳐 쓸 것.

## 배운 점

**계층을 제대로 나눠두면 저장소 전환이 정말 "구현체만 바꾸면" 끝난다.** Domain(자기 상태
검증) → Repository(순수 저장/조회) → Service(흐름 지휘)로 나눠두고 `typing.Protocol`로
경계를 그은 덕분에, Memory → JSON → Postgres/Redis로 세 번 저장소를 바꾸는 동안 서비스
코드(`account/services/`, `card/services/`, `billing/services/`, `orchestration/service.py`)를
단 한 줄도 안 고쳤다. "나중에 DB로 바꾸기 쉽게 설계하라"는 조언을 들을 땐 추상적으로
느껴졌는데, 실제로 세 번 바꿔보고 나서야 이게 무슨 뜻인지 체감했다.

**LLM 에이전트는 설계 문서만으로는 절대 다 못 검증한다.** 자동화 테스트 199개가 전부
통과해도, 실제 Gemini API로 한 번 돌려보니 완전히 새로운 종류의 문제(아래 참고)가
나왔다. 프레임워크 관련 코드는 "실제로 돌려보고 확인한 뒤에 설계·구현한다"는 원칙을
지켜온 게(예: `interrupt()`가 재개 시 노드를 처음부터 재실행하는지 스크립트로 먼저
확인) 이번에도 그대로 적용됐다 — 다만 이번엔 그 대상이 프레임워크가 아니라 모델
자체의 행동이었다는 게 달랐다.

**"로컬에서 됨"과 "실제 프로덕션에서 됨" 사이의 간극이 생각보다 크다.** 브랜치 이름,
컨테이너 베이스 이미지에 특정 바이너리가 있는지, 공유 비밀번호에 URL 특수문자가 있는지 —
전부 로컬 테스트로는 절대 안 드러나고 실제로 배포해봐야만 나오는 문제였다.

## 어려웠던 점과 해결 과정

1. **조회 요청조차 응답이 완전히 비어 있었다.** 실제 API 키로 처음 돌려봤을 때 "내 계좌
   목록 보여줘" 같은 단순 조회조차 빈 응답이 왔다. tool을 1개씩 늘려가며 재현 조건을
   좁혀보니 15개 이상 tool을 bind하면 모델이 `thinking_budget`(기본값 -1, "동적")을 전부
   써버리고 tool 호출도 텍스트도 없이 끝나버리는 걸 확인했다. 고정값(1024)으로 해결.
2. **이체 요청을 했는데 tool을 안 부르고 채팅으로 먼저 되물었다.** 처음엔 버그인 줄
   알았는데, 원인을 보니 시스템 프롬프트가 "tool 자체가 승인을 담당한다"는 걸 명시하지
   않아서 모델이 나름대로 안전하게 행동한 것이었다. 별명("생활비")을 ID로 못 바꿔서
   계좌를 못 찾겠다고 답하는 문제도 같이 발견 — 규칙을 명시하고 few-shot 예시를 넣어 해결.
3. **배포 파이프라인이 실행조차 안 됐다.** TIL 템플릿을 그대로 복사하면서 브랜치를
   `master`로 뒀는데, 이 저장소 기본 브랜치는 `main`이었다. 실제로 push해보기 전까지는
   전혀 몰랐던 문제.
4. **Redis 연결이 `localhost:3`으로 시도되는 황당한 에러.** 공유 Redis 비밀번호에
   `openssl rand -base64`가 생성하는 `/`, `+`, `=` 같은 URL 특수문자가 들어있었는데, 이걸
   URL 인코딩 없이 그대로 접속 문자열에 넣어서 파서가 host:port를 엉뚱하게 잘랐다.
   `urllib.parse.quote()`로 인코딩해서 해결.
5. **컨테이너는 떠 있는데 계속 unhealthy.** `docker-compose.yml`의 헬스체크가 `wget`을
   쓰는데, 정작 베이스 이미지(`python:3.13-bookworm-slim` 계열)엔 `wget`이 없었다. Python
   표준 라이브러리로 헬스체크를 바꿔서 해결.

## 남은 한계와 개선하고 싶은 점

- 시스템 프롬프트가 아직 100% 안정적이진 않다 — 별명으로만 지칭했을 때 가끔 확인 질문을
  먼저 하는 경우가 남아있을 수 있어서, few-shot을 더 늘리거나 아예 파라미터를 구조화된
  형태로 강제하는 방향을 고려해볼 만하다.
- LangGraph 체크포인터가 `InMemorySaver`(휘발성)라, 서버가 재시작되면 진행 중이던 "대화
  맥락"은 날아간다(승인 대기 자체는 Postgres/Redis에 있어서 안전하지만). 여러 인스턴스로
  수평 확장하려면 `langgraph-checkpoint-postgres` 같은 걸로 바꿔야 한다.
- 이 환경에 Terraform 바이너리가 없어서 ECR 리소스를 `aws ecr` CLI로 직접 만들었다 —
  실제 Terraform state 밖에 있는 상태라, 나중에 `terraform import`로 편입해야 한다.
- 두 계좌 사이의 반대 방향 동시 이체(A→B, B→A)가 겹치면 `SELECT ... FOR UPDATE` 잠금
  순서가 엇갈려 데드락이 날 수 있는 이론적 가능성이 있다 — 지금 규모에선 Postgres가 자동
  감지해 한쪽을 에러로 중단시키는 것으로 충분하다고 보고 별도 처리는 안 했다.
- 계좌/카드/청구서를 "생성"하는 기능 자체가 없어서 데모 데이터에 의존한다 — 처음부터
  "기존 것을 다루는" 기능만 요구받았기 때문.
- 조건부 이체·분할 이체·카드 재발급·청구서 일괄납부 같은 나머지 실행형 액션은 자동화
  테스트로는 검증됐지만, 실제 Gemini와의 대화로는 아직 확인 안 해봤다.
