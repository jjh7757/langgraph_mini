# Agent 패키지 설계

`4_아키텍처_대화승인계층.svg`의 `LangGraph Agent → Propose Tools → Orchestration Service`를
실제 LangGraph 그래프로 옮기는 마지막 조각. Orchestration은 이미 완성돼 있으니, 여기서는
"LLM이 자연어를 어떻게 구체적인 action/params/request_id로 바꾸는가"와 "승인·거절·수정을
`interrupt()`/`Command(resume=...)`로 어떻게 받는가"만 정하면 된다.

## 1. 두 가지 미리 정한 것

**request_id = tool_call_id.** LangGraph는 `interrupt()` 이후 재개(resume)될 때 그 노드
함수를 처음부터 다시 실행한다 — 그래서 `interrupt()` 호출 전에 `request_id`를 uuid4 같은
걸로 즉석에서 만들면 재실행마다 값이 달라져 멱등성이 깨진다. 대신 LLM의 tool call에
LangChain이 이미 붙여주는 안정적인 `tool_call_id`(`InjectedToolCallId`로 주입받음)를
`request_id`로 그대로 쓴다 — 같은 tool call은 재실행돼도 같은 id.

**자연어 해석 = `interrupt()` + 전용 분류 LLM 호출.** `propose_*` tool 함수 안에서
`orchestration.propose()` 후 `interrupt(요약)`으로 멈추고, 재개 시 돌아온 raw 텍스트를
작은 구조화 출력 LLM 호출로 분류(승인/거절/수정+새 params)해서 바로
`approve`/`reject`/`revise`를 부른다. 메인 에이전트 LLM 입장에서는 tool 호출 한 번으로
보임(중간 과정이 안 보임) — `confirm_pending` 같은 별도 tool을 노출하지 않는다.

## 2. 폴더 구조

```
agent/
    __init__.py
    context.py          # AgentContext(requester_id, thread_id) + get_context()
    confirmation.py     # ConfirmationDecision + classify_confirmation() + 승인 루프
    propose_tools.py    # @tool 함수 22개 (실행형 12 + 조회형 10)
    graph.py             # StateGraph 조립 — 복구 체크 노드 + 에이전트 노드 + ToolNode
    wiring.py             # OrchestrationService 등 실제 구현체 조립(JSON 파일 경로 등)
```

당초 계획(`폴더_구조.md`)엔 3개뿐이었는데, 승인 루프 로직이 12개 tool에 전부 중복되는 걸
막으려고 `confirmation.py`로 뺐고, "실제 파일 경로로 무엇을 조립할지"를 그래프 정의 자체와
분리하려고 `wiring.py`를 추가했다.

## 3. context.py — requester_id는 LLM이 못 정하게

```python
@dataclass
class AgentContext:
    requester_id: str
    thread_id: str


def get_context() -> AgentContext:
    """현재 실행 중인 RunnableConfig의 configurable에서 꺼냄.
    requester_id는 절대 LLM이 tool 인자로 넘기게 하지 않음(그러면 LLM이 남의 id로
    요청하는 걸 못 막음) — 항상 이 함수를 통해서만, 즉 그래프를 invoke할 때
    config={"configurable": {"thread_id": ..., "requester_id": ...}}로 넘겨받은 값만 씀."""
```

`thread_id`는 LangGraph의 checkpointer가 원래 쓰는 값과 같은 걸 그대로 재사용(대화 스레드 =
Orchestration의 thread_id) — 두 개를 따로 관리 안 함.

## 4. confirmation.py — 승인 루프 (모든 실행형 tool이 공유)

```python
class ConfirmationDecision(BaseModel):
    action: Literal["approve", "reject", "revise", "unrelated"]
    new_params: dict | None = None  # action == "revise"일 때만


def classify_confirmation(reply: str, request: PendingRequest) -> ConfirmationDecision:
    """작은 구조화 출력 LLM 호출. 프롬프트에 request.action/params 요약 + reply를 주고
    분류만 시킴 — 메인 에이전트와 별개의(더 싸고 빠른) 모델 호출.
    "unrelated"는 복구 체크 노드에서만 의미 있음(6절 참고) — 방금 막 제안한 직후의
    확인 루프에서는 나올 일이 거의 없지만 방어적으로 넣어둠."""


def confirm_loop(request: PendingRequest, ctx: AgentContext) -> ActionResult:
    """PENDING인 동안 반복:
    1) interrupt(_summarize(request))로 멈추고 사용자 raw 답변을 받음
    2) classify_confirmation으로 분류
    3) approve → orchestration.approve(request.request_id) 반환하고 끝
       reject → orchestration.reject(...) 후 "거절됨" ActionResult 반환하고 끝
       revise → orchestration.revise(...)로 params 갱신 → request 갱신하고 1)로 돌아가
                (전체 내용을 다시 보여주고 재승인받음 — "승인 전 수정" 요구사항)
       unrelated → 이 함수 밖(6절)에서만 나옴; 여기 루프에선 approve 취급하지 않고
                   그대로 다시 interrupt해서 재차 확인 요청(무한루프 방지용 처리는
                   구현 시 반복 횟수 제한 등으로 보강)
    """


def propose_and_confirm(action: str, params: dict, ctx: AgentContext, request_id: str) -> ActionResult:
    """새 제안 시작점. orchestration.propose() 후 confirm_loop() 그대로."""


def resume_and_confirm(request: PendingRequest, ctx: AgentContext) -> ActionResult:
    """재시작 복구용 — 이미 있는 PendingRequest를 propose 없이 confirm_loop()로 바로."""
```

## 5. propose_tools.py — 실행형/조회형 각각 22개

실행형(12개, `propose_and_confirm` 그대로 위임) 예시:

```python
@tool
def block_card_as_lost(
    card_id: str, tool_call_id: Annotated[str, InjectedToolCallId]
) -> str:
    """카드를 분실 정지합니다. 실행 전 사용자 승인이 필요합니다."""
    result = propose_and_confirm(
        "card.block_as_lost", {"card_id": card_id}, get_context(), tool_call_id
    )
    return _format(result)
```

조회형(10개, 승인 없이 바로):

```python
@tool
def get_account(account_id: str) -> str:
    """계좌 정보를 조회합니다."""
    account = orchestration.query(
        "account.get_account", {"account_id": account_id}, get_context().requester_id
    )
    return _format_account(account)
```

12+10 = 22개, `orchestration/actions.py`의 ACTIONS 목록과 정확히 1:1 대응. 도구 이름/설명
(docstring)이 LLM이 보는 전부라 여기 문구가 실제로 중요함 — 실제 구현 시 사용자가 준
"사용자 요청" 예문들을 docstring에 참고 문구로 남겨두면 tool-calling 정확도에 도움이 됨.

## 6. graph.py — 그래프 구조

```
START
  → check_recovery   (get_pending(thread_id) 확인)
       있으면 → resume_and_confirm()으로 그 자리에서 확인부터 받고 끝
       없으면 →
  → agent            (LLM + 22개 tool bind, 평소 ReAct 루프)
       tool 호출 필요 → ToolNode(그 안에서 필요하면 tool이 스스로 interrupt())
       아니면 → END
```

**check_recovery의 "unrelated" 처리**: 복구 체크 시점엔 사용자의 새 메시지가 "그 pending에
대한 답"인지 "완전히 새로운 요청"인지 불확실함(막 제안 직후와 다름). `classify_confirmation`이
`unrelated`를 반환하면 그 pending은 그대로 둔 채 그냥 `agent` 노드로 넘어감(무시하지 않고
나중에 사용자가 다시 언급하면 그때 처리) — 대신 시스템 프롬프트에 "지금 승인 대기 중인
요청이 있다"는 걸 컨텍스트로 한 줄 얹어줘서 메인 에이전트가 필요하면 스스로 언급하게 함.

**checkpointer**: `interrupt()`/`Command(resume=...)`을 쓰려면 LangGraph checkpointer가
필수(없으면 애초에 동작 안 함). 그런데 "재시작 복구"의 정확성 자체는 checkpointer가 아니라
Orchestration의 JSON PendingRepo에 이미 들어있음 — 프로세스가 재시작돼서 checkpointer가
그 스레드의 중단 지점을 기억 못 해도(예: 휘발성 `MemorySaver`), 다음 사용자 메시지가 오면
그냥 새 실행으로 `check_recovery`부터 다시 타면서 `get_pending`으로 알아서 찾는다. 그래서
지금 단계에선 **`MemorySaver`(휘발성)로 충분** — 같은 프로세스 안에서 단일 대화 턴 중
interrupt/resume이 동작하기만 하면 됨. 나중에 여러 서버 인스턴스로 확장하거나 프로세스 내
재시도까지 완벽히 다루고 싶어지면 그때 durable checkpointer(SqliteSaver 등, 새 의존성 필요)로
교체 — Orchestration 쪽 로직은 전혀 안 바뀜.

## 8. Agent 프롬프트가 대신 책임지는 부분 (코드로 안 만드는 것)

- **"이체해줘"처럼 정보 부족** → 시스템 프롬프트가 "부족하면 tool 호출 전에 되물어라"라고
  지시. `propose_and_confirm`의 `required_params` 체크(Orchestration의 `MissingParamsError`)는
  최후 안전망일 뿐.
- **"저축으로 10만원 옮겨줘"처럼 후보 여러 개, "그 카드 잠가줘"처럼 대화 맥락** → 메인
  에이전트 LLM이 `get_accounts`/`get_cards` 조회 tool + 대화 히스토리로 스스로 판단. 별도
  코드 없음.
- 전부 프롬프트 엔지니어링 영역이라 이 설계 문서에서 세부 문구까지는 안 정함 — 실제 구현
  때 시스템 프롬프트 초안을 같이 검토.

## 9. 구현 완료 (2026-09-28)

`agent/` 전체(context/confirmation/propose_tools/graph/wiring) 구현 완료, 테스트 22개
(context 3 + confirmation 8 + propose_tools 6 + graph 5). 설계 대비 실제로 부딪혀서
고친 부분들:

- **복구 시 이미 와 있는 답변을 또 물어보면 안 됨** — 애초 설계엔 없던 버그. 재시작 후
  `check_recovery`가 무조건 `resume_and_confirm` → `interrupt()`를 부르면, 사용자가 이미
  보낸 새 메시지("응 진행해줘")를 무시하고 또 물어보게 됨. `confirm_loop`에
  `initial_decision`을 추가해서, `check_recovery`가 그 메시지를 먼저 한 번만 분류하고
  결과를 넘겨주는 식으로 고쳤다(6절 마지막 문단 참고, `classify_confirmation` 중복 호출도
  피함). `test_recovery_after_restart_resolves_pending_without_reasking_llm`이 이걸
  검증 — 메인 에이전트 LLM이 그 턴에 아예 안 불려야 통과함.
- **request_id = tool_call_id, revise 루프가 진짜 재실행에도 안전한지** —
  `langgraph.types.interrupt`가 노드/tool 함수를 처음부터 재실행한다는 걸 실제로
  확인(재실행 시 이전 print가 다시 찍힘)한 뒤 그대로 코드로 옮김. `confirm_loop`가
  여러 번 `interrupt()`를 도는 것도(revise 루프) 실제 그래프로 검증함.
- `MAX_REVISIONS = 5`로 확정(같은 확인 흐름 안에서 "수정" 반복 상한)
- `classify_confirmation`/메인 에이전트 LLM 전부 생성자 인자로 주입받게 설계
  (`build_graph(llm, orchestration, confirmation_llm=None)`) — 테스트에서 실제 Gemini
  호출 없이 `bind_tools`/`invoke`만 흉내 낸 가짜 LLM으로 그래프 전체를 검증할 수 있었음
- 조회형 tool(`get_my_cards` 등)은 `owner_id`를 LLM 인자로 안 받고 항상
  `get_context(config).requester_id`로 채움 — LLM이 남의 id를 넣을 수 있는 경로 자체를
  없앰(Orchestration의 `verify_is_self`는 그대로 안전망으로 남아있음)

## 10. 아직 안 정한 것 (agent 패키지 밖의 일)

- 실제 `ChatGoogleGenerativeAI` 인스턴스를 만들어서 `build_graph`/`build_orchestration`을
  실행하는 진입점(스크립트) — 지금은 `llm`/`orchestration`을 인자로 받게만 설계해둠
- 시스템 프롬프트 초안 — 기능표의 "사용자 요청" 예문들을 few-shot으로 넣을지
- `wiring.py`의 data 디렉터리 경로를 환경변수로 뺄지(지금은 인자 기본값 "data")
- `classify_confirmation`이 실제로 어떤 모델을 쓸지(메인 에이전트와 같은 모델 재사용 vs
  더 싼 모델) — 지금은 `confirmation_llm` 생략 시 `llm`을 그대로 재사용
