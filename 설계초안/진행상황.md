## 전체 아키텍처 (CLI + 웹 배포까지 구현 완료)

```
Client
  → CLI(cli.py, 터미널)                 ← 로컬 데모용, 계속 유지
  → 웹 채팅(api/app.py + static/chat.html, 순수 HTML — React 아님)  ← AWS 배포용, 신규
    → LangGraph Agent (agent/graph.py — LLM + 22개 tool, ReAct 루프) ← 둘 다 이 그래프를 그대로 재사용, 무변경
      → Propose Tools (agent/propose_tools.py — 제안만, 실행 없음)
        → Orchestration Service (승인·되묻기·복구 + PendingRepo/CompletedRequestRepo)
          → [승인 후에만 호출] AccountService / CardService / BillingService
            → 각자 Repository → Memory(테스트) / JSON 파일(CLI 로컬용) / Postgres+Redis(웹 배포용, 구현 완료)
```

AWS 배포는 신규 인프라(RDS/ElastiCache/ECS/App Runner 등)를 만들지 않고, jjh7757/TIL에 이미
구축된 **기존 상시 EC2(deploy-server) + Caddy + 공용 Postgres/Redis 컨테이너**를 그대로
재사용하는 세 번째 앱(`virtual-financial-services`)으로 얹는 방식으로 확정·구현됨:

```
git push → GitHub Actions(OIDC) → ECR → SSM으로 EC2에서 docker compose pull && up -d
EC2(기존) ── Caddy(:80/:443, 기존) ── virtual-financial-services 컨테이너(FastAPI, 신규)
                                          → 공용 postgres/redis 컨테이너(기존 서버 안, database만 새로 생성)
```

Terraform은 이 앱 때문에 새로 생기는 ECR 리포지토리만 관리(`infra/terraform/`) — IAM 신뢰
정책은 다른 앱(`deploy-test`/`rag`)과 공유하는 역할이라 기존 수동 방식(AWS CLI) 유지.

**핵심 결정 사항 (전부 코드에 반영됨)**
- Java `interface` 대신 Python `typing.Protocol` 사용, 구현체에 `Impl` 접미사 안 붙임(`Default...` 또는 역할 이름)
- 계층 책임: Domain(자기 상태 검증) → Repository(순수 저장/조회) → Service(흐름 지휘)
- 소유권 검증 / 멱등성(request_id) / 예외→구조화 결과 변환은 전부 Orchestration Service 책임 — 도메인 서비스는 이 중 아무것도 모름
- `account`/`card`/`billing`은 서로 동급인 최상위 패키지(다이어그램대로) — Card를 Account 안에 얹어두지 않음. account만 카드결제 거래내역 표시를 위해 card 패키지를 가져다 씀(반대 방향 의존 없음)
- 저장 방식은 **Memory(테스트용) → JSON 파일(CLI 로컬용) → Redis/Postgres(웹 배포용)** 3단계로 확정 — 당초 "Pending은 메모리, 완료 이력은 바로 Postgres"였던 계획을 재시작 복구 요구사항 때문에 JSON 단계를 추가하는 걸로 수정함. Postgres/Redis 전환은 배포 전에(트래픽과 무관하게) 완료 — 이유: 트랜잭션 경계·동시성 제어가 전혀 없던 상태로 실제 서버에 올리는 게 더 위험하다고 판단(아래 참고)
- Orchestration은 액션마다 propose_x/approve_x 메서드를 만드는 대신 **"action 문자열 + params dict"로 범용 디스패치**(`ACTIONS` 레지스트리) — 실행형 12개 + 조회형 10개, 총 22개
- Agent 쪽 `request_id`는 LangChain의 `tool_call_id`를 그대로 씀 — `interrupt()` 재개 시 노드가 처음부터 재실행되므로 즉석 uuid 생성은 멱등성이 깨짐(실제로 스크립트로 재실행 동작을 확인하고 내린 결정)
- 자연어 승인/거절/수정 해석은 `interrupt()` + 전용 분류 LLM 호출로 처리(메인 에이전트에겐 tool 호출 한 번으로 보임)
- 재시작·장애 복구는 "PENDING 상태만으로 절대 자동 실행 안 함"이 불변식 — LangGraph checkpointer가 아니라 Orchestration의 PendingRepo(JSON 또는 Redis)가 이 정확성을 담당(checkpointer는 휘발성 `InMemorySaver`로 충분, 이유는 `에이전트_설계.md` 6절). 웹 배포에서도 그래프 객체를 프로세스 전체에서 하나만 재사용해 이 성질을 그대로 유지(`db/postgres.py` 모듈 docstring 참고)
- 배포 시 FastAPI 레이어는 **얇게 얹기만** 하고 `agent/`·`orchestration`·`account`·`card`·`billing`은 무변경 — 실제로 `api/app.py`가 `cli.py`의 `_repl`/`_run_and_handle`과 완전히 같은 흐름을 HTTP로만 감쌈(React 같은 프론트엔드 프레임워크 없이 순수 HTML/JS 채팅 페이지 하나)
- SQL 레포지토리는 Protocol 시그니처를 그대로 유지하되, 단건 조회(`find_by_id` 계열)에 `SELECT ... FOR UPDATE`를 추가해 동시성 제어를 서비스 코드 변경 없이 확보. DB 쓰기는 HTTP 요청(에이전트 한 턴) 단위로 트랜잭션이 걸리도록 `db/postgres.py`가 contextvar로 "현재 커넥션"을 주입(그래프는 프로세스 전체에서 하나 유지해야 하는 요구와 충돌하지 않게 하기 위함 — 자세한 이유는 그 파일 docstring)
- Redis는 PendingRepo 전용이라는 결정대로, 요청이 PENDING이 아니게 되면(승인/거절 후) Redis 키를 지우고 완료 이력은 Postgres에만 영구 보관(`orchestration/pending_repository_redis.py`)

## 참고: 계속 지켜온 작업 방식

- 구현 전 항상 설계 문서화(막히는 지점은 사용자에게 직접 질문) → 리뷰 → 코드 순서
- Card 모듈은 처음엔 "뼈대만"(스켈레톤) 요청받아 사용자가 직접 구현했고, 이후 Billing/Orchestration/Agent/CLI는 "전부 구현해줘" 요청으로 Claude가 끝까지 구현 — 두 방식 다 나온 적 있으니 매번 어느 쪽인지 확인할 것
- 프레임워크(LangGraph/LangChain) 관련 코드는 추측으로 안 짜고, 실제 설치된 버전으로 작은 스크립트를 먼저 돌려서 API 동작(예: `interrupt()`가 재개 시 함수를 처음부터 재실행하는지)을 확인한 뒤 그 결과를 근거로 설계·구현함
- 버그 수정 후 반드시 `uv run python -m pytest`로 검증하고 커밋
- 커밋 메시지는 한글로, 변경 이유를 구체적으로 남김. 논리적으로 분리되는 변경은 커밋도 나눔
- `git add`는 항상 `-A -- ':!**/__pycache__'`로(파이썬 캐시 제외), 매번 커밋 전 `git status --short`로 뭐가 올라가는지 확인
- **여러 세션이 동시에 이 저장소를 건드릴 수 있음** — 작업 시작 전 `git status`/`git diff`로 커밋 안 된 변경이 있는지 항상 먼저 확인할 것(이번에 배포 설계 문서가 그렇게 발견됨)
