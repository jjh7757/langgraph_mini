## 전체 아키텍처 (확정)

```
Client
  → LangGraph Agent (Tool 호출 제안, LLM)
    → Propose Tools (제안만 함, 실행 없음)
      → Orchestration Service (승인·되묻기·복구 + PendingRepo)
        → [승인 후에만 호출] AccountService / CardService / BillingService
          → 각자 Repository → (지금) 메모리 단독 / (확장 후) 공유 PgSession
```

**핵심 결정 사항**
- Java `interface` 대신 Python `typing.Protocol` 사용, 구현체에 `Impl` 접미사 안 붙임(`Default...` 또는 역할 이름)
- 계층 책임: Domain(자기 상태 검증) → Repository(순수 저장/조회, 비즈니스 로직 없음) → Service(흐름 지휘)
- **소유권 검증 / 멱등성(request_id) / 예외→구조화 결과 변환은 전부 Orchestration Service 책임** — AccountService 등 도메인 서비스에는 안 넣기로 확정
- Redis는 **PendingRepo(승인 대기 상태) 전용**으로만 쓰기로 확정 (다른 캐시 용도 아님)
- 완료된 요청 이력은 Redis가 아니라 Postgres에 영구 보관 (Redis는 TTL로 사라지는 임시 데이터용)
- 별명(nickname) 중복 금지는 **같은 owner_id 내에서만** (다른 소유자끼리는 겹쳐도 됨)
- 조건부 이체는 계산(`calculate_conditional_transfer`)과 실행(`confirm_conditional_transfer`)을 분리 — 이게 나중에 Orchestration 전체에 적용된 "제안-승인-실행" 패턴의 원형

## 아직 안 만든 것

- **CardService / BillingService** — 다이어그램에만 박스로 존재, 코드 전혀 없음. Account와 같은 패턴(domain/repository/service 3계층)으로 만들면 됨
- **Orchestration Service** — 승인(interrupt/resume)·되묻기·PendingRepo 연동 전부 미구현
- **PendingRepo** — 지금은 메모리(dict) 계획, 나중에 Redis
- **실제 LangGraph 연동** — Tool 스키마 작성, Context(승인 상태·requester_id) 주입 방식, `@tool` 래핑 등 전부 미착수
- **Postgres 연동** — `SqlAccountRepository` 등 실제 구현 없음, `PgSession`도 개념만 있고 실제 코드 없음
