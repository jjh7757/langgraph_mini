# Orchestration Service 설계

`4_아키텍처_대화승인계층.svg` 구조를 코드로 옮기기 전에 정리하는 문서. 여기 정리된 걸
기준으로 리뷰 후 `orchestration/` 폴더를 채운다 (account/card/billing과 같은 순서:
설계 → 도메인 → repository → service).

## 1. 역할 재확인

```
LangGraph Agent → Propose Tools(제안만, 실행 없음) → Orchestration Service → 도메인 서비스
```

Orchestration이 전담하기로 이미 정한 것 (저장소 루트의 `진행상황.md` 참고):
- 소유권 검증
- 멱등성(request_id — 같은 요청 두 번 실행 안 함)
- 예외 → 구조화 결과 변환
- 승인·되묻기·복구

도메인 서비스(Account/Card/Billing)는 이 중 아무것도 모른다 — 그냥 자기 비즈니스 규칙만
지킨다.

## 2. 요구 기능 → 설계 요소 매핑

사용자가 준 9개 기능을 그대로 놓고, 각각을 Orchestration의 어떤 부분이 담당하는지 정리.
**Orchestration 책임**과 **Agent(LLM) 책임**을 구분하는 게 핵심 — Orchestration은 자연어를
전혀 모른다, 항상 이미 해석된 action/params/request_id를 받는다.

| 기능 | 담당 | 설계 요소 |
|---|---|---|
| 승인·거절 | Orchestration + Agent | `propose`/`approve`/`reject`. 중단·재개 자체는 LangGraph의 `interrupt()`(Agent 그래프 노드가 호출) — Orchestration은 그 앞뒤(제안 생성/승인 처리)만 담당 |
| 변경 결과 저장·조회 | Orchestration(저장 방식) | **JSON 파일 기반 repository** 필요 (3절) |
| 불완전/실행불가 요청 안내 | 주로 Agent, Orchestration은 안전망 | `ActionSpec.required_params` 검증 → `MissingParamsError` |
| 추가 질문(후보 여러 개) | Agent | Orchestration은 후보 목록을 돌려주는 조회(query)만 제공, 되묻기 자체는 Agent가 함 |
| 승인 전 수정 | Orchestration | `revise()` — 기존 PendingRequest의 params만 바꿔서 재확인 |
| 자연어 승인·취소 | Agent(해석) + Orchestration(조회) | Agent가 "응"/"취소"를 approve/reject로 매핑하려면 먼저 request_id를 알아야 함 → `get_pending(thread_id)` |
| 후속 결과 조회 | Orchestration | `get_history(thread_id)` — CompletedRequestRepo를 thread_id로 조회 |
| 대화 대상 확인(후보 여러 개) | Agent | 마찬가지로 참조 해소는 Agent 몫, Orchestration은 조회만 제공 |
| 재시작·장애 복구 | Orchestration | **불변식**: PENDING 상태만으로 절대 자동 실행 안 함. 복구는 `get_pending(thread_id)`로 다시 보여주는 것뿐 — 실행은 항상 새 `approve()` 호출이 있어야만 일어남 |

## 3. 저장 방식 — JSON 파일 (중요한 변경)

"승인한 경우 Python 함수로 데이터를 변경하고 JSON에 저장한다", "재시작 후 진행 중이던
업무를 확인"이라는 두 요구사항을 합치면, **순수 인메모리 dict로는 불가능**하다 — 프로세스가
꺼지면 그 상태도 같이 사라지니까. 그래서 `최종설계자료/폴더_구조.md`에 적어뒀던 "PendingRepo는 지금
메모리, 나중에 Redis"를 다음으로 고친다:

```
지금: JSON 파일 (재시작에도 살아남음, 구현 간단)
나중: PendingRepo → Redis, 완료 이력 → Postgres (확장 시)
```

영향 범위: `account`/`card`/`billing`의 Memory* repository들도 이번 단계에서 JSON 버전이
필요하다 — "조회 요청에는 저장된 데이터를 바탕으로 현재 잔액이나 카드 상태를 안내"하려면
그 계좌/카드 데이터 자체가 프로세스 재시작에도 살아남아야 하기 때문. `Protocol` 기반으로
설계해둔 덕분에 교체 비용은 낮다 (`구현_가이드라인.md`에서 의도했던 그대로).

파일 하나당 엔티티 하나 (`data/accounts.json`, `data/cards.json`, `data/bills.json`,
`data/pending_requests.json`, `data/completed_requests.json`). 각 `JsonXRepository`는
생성자에서 파일을 읽어 메모리에 dict로 올려두고, `save()`할 때마다 전체를 다시 써서
디스크에 반영하는 단순한 방식으로 충분 (지금 규모에서 트랜잭션/락 걱정 안 함 — Memory
버전의 동시성 미보장과 같은 수준의 한계를 그대로 인정).

파일별 위치는 각자 패키지에 (`account/repository_json.py`,
`card/repository_json.py`, `billing/repository_json.py`,
`orchestration/pending_repository_json.py`,
`orchestration/completed_repository_json.py`) — Memory 버전은 테스트용으로 계속 남김.

## 4. 도메인 모델 (`orchestration/domain.py`)

```python
class PendingStatus(Enum):
    PENDING = "대기"
    REJECTED = "거절됨"
    EXECUTED = "완료"
    FAILED = "실패"        # execute가 도메인 예외를 던진 경우

@dataclass
class PendingRequest:
    request_id: str     # 멱등성 키
    thread_id: str       # 대화 스레드 — 복구/자연어 승인/후속 조회 전부 이걸로 찾음
    requester_id: str
    action: str           # ACTIONS의 key
    params: dict
    status: PendingStatus = PendingStatus.PENDING
    result: "ActionResult | None" = None   # 종결(EXECUTED/FAILED/REJECTED) 후 채워짐
    created_at: datetime = field(default_factory=datetime.now)
    resolved_at: datetime | None = None

@dataclass
class ActionResult:
    """예외 → 구조화 변환 결과. 도메인 예외를 그대로 올리지 않고 여기 담아서 반환."""
    success: bool
    value: Any = None
    error_type: str | None = None
    error_message: str | None = None


class NotOwnerError(Exception):
    """요청자가 대상 리소스의 소유자가 아닐 때."""

class ActionNotRegisteredError(Exception):
    """ACTIONS에 없는 action 이름일 때."""

class MissingParamsError(Exception):
    """params에 필수 필드가 빠졌을 때. args에 (action, 빠진 필드 목록)을 담음."""

class PendingRequestNotFoundError(Exception):
    """request_id에 해당하는 PendingRequest가 없을 때."""

class PendingRequestNotPendingError(Exception):
    """이미 처리(승인/거절/완료)된 요청을 다시 approve/reject/revise하려 할 때."""
```

`APPROVED`라는 중간 상태는 안 둠 — `approve()`가 검증부터 실행, 결과 기록까지 한 호출
안에서 끝내기 때문에 영속적으로 남을 "승인은 됐지만 아직 실행 전" 상태가 없음(그런 상태가
있으면 "이전 승인만으로 자동 실행" 오해가 생기기 쉬움 — 아예 그 상태 자체를 없앰).

## 5. 저장소 두 개

**PendingRepo** (`orchestration/pending_repository.py`) — 지금 JSON 파일. "대기 중이거나
최근에 끝난" 것.

```python
class PendingRepository(Protocol):
    def find_by_id(self, request_id: str) -> PendingRequest: ...
    def find_by_thread_id(self, thread_id: str) -> list[PendingRequest]: ...
    def save(self, request: PendingRequest) -> None: ...
```

**CompletedRequestRepo** (`orchestration/completed_repository.py`) — 지금 JSON 파일,
나중에 Postgres(영구). 멱등성의 진짜 근거이자 "후속 결과 조회"의 근거.

```python
class CompletedRequestRepository(Protocol):
    def find_by_request_id(self, request_id: str) -> PendingRequest | None: ...
    def find_by_thread_id(self, thread_id: str) -> list[PendingRequest]: ...
    def save(self, request: PendingRequest) -> None: ...
```

## 6. 액션 레지스트리 (generic dispatch)

```python
@dataclass
class ActionSpec:
    required_params: list[str]                  # propose() 진입 시 이거 다 있는지만 확인
    verify_owner: Callable[[dict, str], None]    # (params, requester_id) -> None, 실패 시 NotOwnerError
    execute: Callable[[dict, "Services"], Any]   # (params, services) -> 실행 결과

ACTIONS: dict[str, ActionSpec] = {
    "card.block_as_lost": ActionSpec(
        required_params=["card_id"],
        verify_owner=lambda p, rid: verify_card_owner(p["card_id"], rid),
        execute=lambda p, services: services.card_status.block_as_lost(p["card_id"]),
    ),
    "billing.pay_bills": ActionSpec(
        required_params=["account_id", "bill_ids"],
        verify_owner=lambda p, rid: (
            verify_account_owner(p["account_id"], rid),
            [verify_bill_owner(bid, rid) for bid in p["bill_ids"]],
        ),
        execute=lambda p, services: services.bill_payment.pay_bills(
            p["account_id"], p["bill_ids"]
        ),
    ),
    # ... 8절 액션 목록 전부 이런 식
}
```

## 7. OrchestrationService 흐름

```python
class OrchestrationService:
    def query(self, action: str, params: dict, requester_id: str) -> Any:
        """조회형. 승인 없이 바로 실행.
        1) ACTIONS에서 spec 조회 (없으면 ActionNotRegisteredError)
        2) required_params 확인 (없으면 MissingParamsError)
        3) spec.verify_owner(params, requester_id) — 실패 시 NotOwnerError
        4) spec.execute(params, self._services) 결과 그대로 반환
        """

    def propose(
        self, action: str, params: dict, requester_id: str, thread_id: str, request_id: str
    ) -> PendingRequest:
        """실행형 1단계 — 제안만, 아직 도메인 서비스 호출 안 함.
        1) completed_repo.find_by_request_id(request_id) — 있으면 그대로 반환 (멱등성)
        2) ACTIONS에서 spec 조회 (없으면 ActionNotRegisteredError)
        3) required_params 확인 (없으면 MissingParamsError — "불완전한 요청" 안전망)
        4) spec.verify_owner(params, requester_id) — 실패 시 NotOwnerError
           (여기서 막히면 PendingRequest 자체를 안 만듦)
        5) 새 PendingRequest(status=PENDING) 만들어 pending_repo에 save, 반환
        """

    def revise(
        self, request_id: str, new_params: dict, requester_id: str
    ) -> PendingRequest:
        """승인 전 수정 ("아니, 5만 원만"). 새 요청을 만들지 않고 기존 것의 params만 바꿈.
        1) pending_repo.find_by_id(request_id) — 없으면 PendingRequestNotFoundError
        2) status != PENDING이면 PendingRequestNotPendingError (이미 끝난 건 못 고침)
        3) request.params를 new_params로 부분 병합(update) — 언급 안 된 필드는 유지
        4) spec.verify_owner(병합된 params, requester_id) 재검증 (대상 자체가 바뀔 수도 있으니)
        5) save 후 반환 — Agent가 이걸로 전체 내용을 다시 보여주고 재승인 받음
        """

    def approve(self, request_id: str) -> ActionResult:
        """실행형 2단계.
        1) pending_repo.find_by_id(request_id) — 없으면 PendingRequestNotFoundError
        2) status != PENDING이면 PendingRequestNotPendingError
        3) ACTIONS[request.action].execute(request.params, self._services) 호출
           - 성공: ActionResult(success=True, value=결과), status=EXECUTED
           - 도메인 예외 발생: ActionResult(success=False, error_type=.., error_message=..),
             status=FAILED
        4) request.result = ActionResult, resolved_at 채워서 pending_repo.save +
           completed_repo.save
        5) ActionResult 반환
        """

    def reject(self, request_id: str) -> PendingRequest:
        """1) find_by_id, 2) status != PENDING이면 PendingRequestNotPendingError,
        3) status=REJECTED로 바꿔 pending_repo/completed_repo 둘 다 저장(거절도 종결이라
        멱등성 대상), 도메인 서비스는 호출 안 함."""

    def get_pending(self, thread_id: str) -> list[PendingRequest]:
        """이 스레드의 PENDING 상태 요청들. 용도 세 가지:
        - 자연어 승인/취소: Agent가 "응"/"취소"를 어떤 request_id에 매핑할지 여기서 찾음
        - 재시작 복구: 프로세스가 다시 뜬 뒤 이 스레드에 진행 중이던 게 있었는지 확인
        - "지금 뭐 승인 대기 중이야?" 같은 직접 질문
        복구 시에도 여기서 나온 걸 그냥 실행하는 게 아니라 사용자에게 다시 보여주고
        새 approve() 호출을 받아야 함 — PENDING 상태만으로 자동 실행 금지."""

    def get_history(self, thread_id: str) -> list[PendingRequest]:
        """후속 결과 조회("아까 이체가 됐어?"). completed_repo.find_by_thread_id 그대로 위임 —
        각 PendingRequest.result로 성공/실패/거절 여부와 처리 내용을 알 수 있음."""
```

## 8. 소유권 검증 함수 (`orchestration/ownership.py`)

리소스 종류별로 owner까지 가는 경로가 다름:

```python
def verify_account_owner(account_repo, account_id: str, requester_id: str) -> None:
    account = account_repo.find_by_id(account_id)  # 없으면 AccountNotFoundError 그대로 전파
    if account.owner_id != requester_id:
        raise NotOwnerError(account_id)

def verify_card_owner(card_repo, account_repo, card_id: str, requester_id: str) -> None:
    card = card_repo.find_by_id(card_id)
    verify_account_owner(account_repo, card.account_id, requester_id)

def verify_reissue_request_owner(reissue_repo, card_repo, account_repo, request_id, requester_id) -> None:
    request = reissue_repo.find_by_id(request_id)
    verify_card_owner(card_repo, account_repo, request.card_id, requester_id)

def verify_bill_owner(bill_repo, bill_id: str, requester_id: str) -> None:
    bill = bill_repo.find_by_id(bill_id)
    if bill.owner_id != requester_id:
        raise NotOwnerError(bill_id)
```

리소스 자체가 없으면(`AccountNotFoundError` 등) 그대로 위로 전파 — 이미 구조화된 도메인
예외라 `approve()`/`query()`의 예외→ActionResult 변환 로직이 그대로 처리.

## 10. Agent와의 경계 (중요)

Orchestration은 자연어를 전혀 다루지 않는다. 정리하면:

- **"이체해줘"처럼 정보 부족** → Agent가 Propose Tool을 아예 호출하지 않고 채팅으로
  되물음(대부분 여기서 끝남). 혹시 불완전한 params로 `propose()`가 호출되면
  `MissingParamsError`가 안전망.
- **"저축으로 10만원 옮겨줘"처럼 후보가 여러 개**("저축"이라는 별명 계좌가 여러 개 등) →
  Agent가 `query("account.get_accounts", ...)`로 후보를 받아서 사용자에게 골라달라고 함.
  Orchestration은 그냥 목록을 돌려줄 뿐 고르는 로직이 없음.
- **"그 카드 잠가줘"처럼 대화 맥락 지시** → Agent(LLM)가 대화 히스토리에서 "그 카드"가
  뭔지 추론. Orchestration은 항상 구체적인 `card_id`만 받음.
- **"응, 진행해"/"취소할게"** → Agent가 `get_pending(thread_id)`로 지금 대기 중인
  request_id를 찾은 뒤 `approve`/`reject` 호출.
