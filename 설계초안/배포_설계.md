## 전체 구조 (요약)

```
Client(React SPA)
  → CloudFront + S3          (정적 파일 서빙)
  → ALB → ECS Fargate         (FastAPI + 기존 LangGraph 에이전트, 변경 없이 재사용)
       → RDS Postgres         (도메인 데이터 + 완료 이력)
       → ElastiCache Redis    (PendingRepo — 승인 대기)
       → Secrets Manager      (Gemini API 키 / DB 자격증명)
       → Gemini API           (외부, google-genai)
```

핵심 원칙: **에이전트/오케스트레이션 로직(`agent/`, `orchestration/`, `account/`, `card/`,
`billing/`)은 그대로 두고, 그 위에 얇은 HTTP 레이어(FastAPI)만 얹는다.** `cli.py`의
`_repl`/`_run_and_handle`이 하던 일(메시지 보내기 → interrupt 나오면 되묻기 → 이어서
실행)을 HTTP 엔드포인트로 옮기는 정도.

## 프론트엔드

- **기술: React + Vite (TypeScript)** — SPA 챗 UI.
  - Next.js 대신 Vite인 이유: 이 프로젝트엔 SSR/SEO가 필요 없는 내부용 대화형 UI라 정적
    SPA로 충분하고, 빌드 산출물을 S3+CloudFront에 그대로 올리면 되므로 배포가 더 단순.
- **화면 구성**: 메시지 리스트 + 입력창(기존 REPL과 동일한 대화 흐름). `interrupt()`로 되묻는
  질문이 오면 일반 메시지와 구분되는 카드로 보여주고, 승인/거절/수정 버튼과 자유 텍스트
  입력을 모두 지원(지금 CLI에서 자연어로 답하면 `classify_confirmation`이 분류하는 방식
  그대로 재사용 — 프론트가 굳이 버튼 3개짜리 구조화된 입력을 강제할 필요 없음).
- **스트리밍**: 초기엔 요청-응답(동기)으로 충분. 토큰 단위 스트리밍이 필요해지면
  WebSocket 대신 **SSE(Server-Sent Events)** — ALB가 별도 설정 없이 그대로 통과시킴.
- **인증**: 초기엔 간단한 로그인(자체 JWT 또는 AWS Cognito Hosted UI) → 요청 헤더의 JWT에서
  `requester_id`를 추출해 지금 하드코딩된 `DEMO_OWNER_ID`를 대체.
- **배포**: `npm run build` 산출물을 S3에 올리고 CloudFront로 서빙, 배포 시 CloudFront
  캐시 무효화까지 CI에서 자동화.

## 백엔드

- **기술: FastAPI (ASGI) + uvicorn** — 지금 `agent/graph.py`, `agent/wiring.py`,
  `orchestration/service.py`는 전혀 안 바꾸고 그 위에 얹기만 함.
- **엔드포인트 초안**:
  | 메서드/경로 | 역할 |
  |---|---|
  | `POST /chat` | `{thread_id, message}` → 에이전트 실행. `interrupt` 나오면 `{status:"needs_confirmation", question}`, 아니면 `{status:"done", answer}` |
  | `POST /chat/resume` | `{thread_id, reply}` → `Command(resume=reply)`로 이어서 실행(승인 응답 처리) |
  | `GET /pending` | 복구 확인용 — `orchestration.get_pending(thread_id)` 그대로 노출 |
  | `GET /chat/stream` | (나중에) SSE로 토큰 스트리밍, `astream_events` 기반 |
- **인증 미들웨어**: JWT 검증 → `config["configurable"]["requester_id"]`에 주입.
- **실행 환경**: Dockerfile로 컨테이너화(`uv sync` 그대로 사용), ECS Fargate 태스크로 실행.
- **⚠️ 지금 결정해야 할 제약**: `graph.py`의 checkpointer가 `InMemorySaver`(휘발성)라서,
  프로세스가 재시작되거나 ECS 태스크가 2개 이상이면 진행 중이던 **대화 메시지 기록**이
  날아감(단, `PendingRepo`/완료 이력은 JSON·나중엔 Postgres·Redis라 안전 — 승인 대기
  자체는 안 사라짐, 대화 맥락만 사라짐). 배포 시 둘 중 하나 선택:
  1. **ECS 태스크를 1개로 고정**(`desired_count=1`) — 가장 간단, 트래픽 적은 지금 단계 추천
  2. `langgraph-checkpoint-postgres`로 교체해 여러 태스크로 수평 확장 가능하게 함 — 트래픽
     늘어나면 나중에

## 데이터 저장소 — JSON → Postgres/Redis 전환

기존에 계획된 대로(6/7번 다이어그램):

- **RDS Postgres**: `account`/`card`/`billing` 도메인 데이터 + `orchestration`의 완료 이력
  (`CompletedRequestRepository`). `*_repository_json.py`를 `*_repository_sql.py`로
  교체하면 됨 — Protocol 기반이라 서비스 코드는 무변경.
- **ElastiCache Redis**: `PendingRepo`(승인 대기) 전용 — 이미 확정된 규칙, 다른 캐시
  용도로 안 씀.
- **전환 순서**: 지금 JSON 그대로 컨테이너화·배포부터 검증 → 그다음 Postgres/Redis 붙이기.
  (한 번에 다 바꾸지 않고 단계적으로 — 지금까지 해온 방식과 동일)

## 인프라 구성 (AWS)

| 컴포넌트 | AWS 서비스 | 역할 |
|---|---|---|
| 프론트 정적 호스팅 | S3 + CloudFront | React SPA 서빙 |
| 백엔드 실행 | ECS Fargate (또는 App Runner) | FastAPI + LangGraph 컨테이너 |
| DB | RDS Postgres (`db.t4g.micro`부터) | 도메인 데이터 + 완료 이력 |
| 캐시/PendingRepo | ElastiCache Redis | 승인 대기 상태 |
| 비밀 관리 | Secrets Manager | Gemini API 키, DB 자격증명 |
| 도메인/인증서 | Route53 + ACM | HTTPS |
| 로그 | CloudWatch Logs | 컨테이너 로그 |
| CI/CD | GitHub Actions → ECR → ECS/App Runner | 백엔드 빌드·배포, 프론트는 S3 sync + CloudFront invalidate |

**ECS Fargate vs App Runner**: 부트캠프 프로젝트 규모엔 **App Runner가 더 간단**(VPC/ALB를
직접 안 만들어도 됨, ECR 이미지만 밀어넣으면 됨). 나중에 세밀한 네트워크 제어나
Redis/RDS를 VPC 안에 붙이는 게 부담스러워지면 그때 ECS+ALB로 옮기는 것도 고려.
지금은 결정 보류 — 프론트/백엔드 코드 완성 후 실제 배포 직전에 정한다.

## 비용/규모 고려

- 처음엔 App Runner(백엔드) + JSON 파일 유지(Postgres/Redis 없이) + S3/CloudFront(프론트)만
  으로 시작 — 월 몇 달러 수준으로 데모 가능.
- 평가/데모가 목적이면 굳이 처음부터 Postgres/Redis를 붙일 필요 없음. 단, 컨테이너
  재시작 시 JSON 파일이 날아가지 않으려면 EFS 마운트 또는 이 시점에 바로 RDS로 전환.
- 실사용/트래픽이 실제로 생기는 단계에서만 Postgres/Redis 전환 진행.

## 아직 안 정한 것
