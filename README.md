# langgraph-mini

LangGraph 기반 계좌·카드·청구서 관리 에이전트. Gemini가 자연어 요청을 이해해 계좌 이체,
카드 정지/재발급, 청구서 납부 같은 **잔액이나 상태를 바꾸는 작업은 항상 사용자 승인을 받은
뒤에만** 실행하고, 조회는 바로 답한다.

## 요구 사항

- Python >= 3.13
- [uv](https://docs.astral.sh/uv/)
- Gemini API 키 ([Google AI Studio](https://aistudio.google.com/apikey)에서 발급)

## 실행 방법

```bash
uv sync
cp .env.example .env   # 이 파일에 GOOGLE_API_KEY 채우기
uv run langgraph-mini
```

터미널에 뜨는 `나>` 프롬프트에 자연어로 입력하면 됩니다. `exit` 또는 `quit`으로 종료.

- **데이터**: `data/*.json`에 저장됩니다. 프로그램을 껐다 켜도 계좌 잔액·카드 상태·청구서
  납부 여부·승인 대기 중이던 요청이 그대로 남아있습니다(재시작 복구).
- **첫 실행**: 이 프로젝트엔 계좌/카드/청구서를 새로 "만드는" 기능이 없어서(기존 것을
  다루는 기능만 구현했음), `data/`가 비어있으면 데모 계좌 2개(생활비 500,000원 / 저축
  2,000,000원), 카드 1개(생활비 체크카드), 청구서 1개(전기요금 45,000원)를 자동으로
  만들어둡니다. 아래 요청 예시들은 전부 이 데모 데이터를 기준으로 합니다.
- **테스트**: `uv run python -m pytest` (199개 통과)

## 구현한 기능

### 계좌

| 기능 | 설명 |
|---|---|
| 계좌 조회 | 잔액·별명 조회, 여러 계좌 잔액 합계 조회 |
| 계좌 별명 변경 | 같은 소유자 내에서만 별명 중복 금지 |
| 이체 | 즉시 이체 / 잔액 중 일정액만 남기고 나머지 이체(조건부) / 여러 계좌로 나눠 이체(분할) |
| 거래내역 조회 | 기간·금액·거래유형 필터, 최근순 정렬 |

### 카드

| 기능 | 설명 |
|---|---|
| 카드 조회 | 이름·종류(신용/체크)·상태 조회 |
| 분실 정지 | 사용가능/일시잠금 상태에서 가능 |
| 일시 잠금 / 잠금 해제 | 분실 정지와 구분됨(잠금 해제로는 분실 정지를 못 풂) |
| 재발급 신청·조회·수정·취소 | 배송지(집/회사) 지정, 이미 신청 있으면 안내, 제작 시작 전까지만 수정·취소 가능 |
| 정지 후 재발급 | 분실 정지와 재발급 신청을 이어서 처리하되 각각 따로 승인받음 |

### 청구서

| 기능 | 설명 |
|---|---|
| 미납 청구서 조회 | 납기일 빠른 순 |
| 단건 납부 | 기한이 지나도 연체료 없이 납부 가능, 이미 낸 건 재처리 안 함 |
| 일괄 납부 | 납기일 빠른 순으로 처리, 잔액 부족 건은 건너뛰고 계속 진행, 저장 실패 시 그 건부터 중단(완료/실패/미처리로 구분해 안내) |

### 대화·승인 (Orchestration + Agent)

| 기능 | 설명 |
|---|---|
| 승인·거절 | 잔액/상태를 바꾸는 요청은 전부 LangGraph의 `interrupt`/`resume`으로 사용자 확인을 거친 뒤 실행 |
| 변경 결과 저장·조회 | 승인된 변경은 JSON 파일에 저장되고, 이후 조회는 그 데이터를 그대로 반영 |
| 불완전한 요청 안내 | 정보가 부족하거나 실행할 수 없는 요청은 이유를 안내하고 되물음 |
| 추가 질문 | 대상이 여러 개면 후보를 보여주고 선택받음 |
| 승인 전 수정 | "아니, 5만 원만" 같은 수정 요청을 반영해 전체 내용을 다시 보여주고 재승인 |
| 자연어 승인·취소 | "응, 진행해"/"취소할게" 같은 자연어를 승인/거절로 해석 |
| 후속 결과 조회 | "아까 이체가 됐어?" — 이전 요청의 성공·실패·취소 여부와 처리 내용 안내 |
| 대화 대상 확인 | "그 카드 잠가줘" 같은 지시어의 대상이 불분명하면 확인, 후보 여러 개면 선택받음 |
| 재시작·장애 복구 | 프로그램이 재시작돼도 승인 대기 중이던 요청을 이어서 확인받을 수 있음(자동 실행은 안 함) |

## 확인해 볼 요청 예시

데모 데이터(생활비 500,000원 / 저축 2,000,000원 / 생활비 체크카드 / 전기요금 45,000원)
기준입니다.

**조회**
- "내 계좌 목록이랑 잔액 보여줘"
- "생활비 계좌 최근 거래내역 보여줘"
- "내 카드 상태 알려줘"
- "아직 안 낸 청구서 있어?"

**이체**
- "생활비에서 저축으로 10만원 이체해줘"
- "생활비 계좌에 50만원만 남기고 저축으로 옮겨줘" (조건부 이체)
- "저축에서 생활비로 20만원, 나한테는 10만원 이렇게 나눠 보내줘" (분할 이체 — 계좌가 더 있어야 의미가 있어 지금 데모 데이터로는 후보 부족 안내로 이어짐)

**카드**
- "생활비 카드 잃어버렸어. 정지해줘"
- "생활비 카드를 집에 둔 것 같아. 잠깐 잠가줘"
- "생활비 카드 찾았어. 잠금 풀어줘"
- "잃어버린 생활비 카드를 집으로 재발급받고 싶어"
- "카드 재발급 신청 상태 알려줘"
- "재발급 카드 배송지를 회사로 바꿔줘"

**청구서**
- "생활비 계좌에서 전기요금 납부해줘"
- "생활비 계좌에서 미납 청구서 전부 납부해줘"

**대화 흐름 (승인/거절/수정)**
- 위 요청 중 하나를 보낸 뒤 → "응 진행해" / "아니 취소할게" / "아니, 절반만"
- "아까 이체가 됐어?" (직전 요청 결과 재확인)
- "그 카드 잠가줘" (바로 앞 대화에서 언급한 카드를 대명사로 지칭)

**의도한 실패/되묻기 상황**
- "이체해줘" (계좌·금액 등 정보 부족 — 되물어야 함)
- "생활비에서 저축으로 -1만 원 옮겨줘" (실행 불가능한 값)

## 구현 기능 동작 확인 결과

Gemini API 호출 자체는 이 환경에 API 키가 없어 직접 재현하지 못했습니다(위 "요청 예시"는
실제 `uv run langgraph-mini`로 사용자가 직접 확인하는 걸 권장합니다). 대신 자연어 해석
아래 있는 실제 실행 로직(Orchestration → 도메인 서비스 → JSON 저장)을 CLI와 동일한 조립
방식(`agent.wiring.build_orchestration`)으로 직접 호출해 성공 시나리오와 직접 선정한 실패
시나리오를 그대로 실행하고 그 결과를 기록했습니다(아래는 실제 실행 출력 그대로).
이 경로들은 `tests/`의 자동화 테스트 199개로도 반복 검증됩니다.

### 성공 시나리오

```
S1. 계좌 목록 조회
  demo-acc-1 | 생활비 | 잔액 500,000원
  demo-acc-2 | 저축 | 잔액 2,000,000원

S2. 카드 목록 조회
  demo-card-1 | 생활비 체크카드 | 체크 | 상태 사용가능

S3. 미납 청구서 조회
  demo-bill-1 | 전기요금 | 45,000원 | 납기 2026-10-08

S4. 정상 이체: 생활비 -> 저축 50,000원 (propose -> approve)
  이체 전: 생활비=500,000 저축=2,000,000
  propose 결과: status=대기
  approve 결과: success=True
  이체 후: 생활비=450,000 저축=2,050,000

S5. 카드 분실 정지 (propose -> approve)
  approve 결과: success=True, 카드 상태=분실정지

S6. 청구서 납부 (propose -> approve)
  approve 결과: success=True
  거래내역: 청구서납부 45,000원

S7. 승인 전 거절(reject) — 카드 일시 잠금 제안 후 거절
  reject 결과: status=거절됨
  (demo-card-1은 S5에서 이미 분실정지 상태라 이 제안이 실행됐어도 실패했을 것 —
   거절이 도메인 호출 자체를 안 하는지 확인하는 용도)
```

### 직접 선정한 실패 시나리오

| # | 시나리오 | 확인 목적 |
|---|---|---|
| F1 | 잔액보다 큰 금액 이체 시도 | 잔액 부족을 구조화된 실패로 반환(예외가 그대로 안 튐) |
| F2 | 이미 납부한 청구서 재납부 시도 | 중복 처리 방지 |
| F3 | 다른 사용자가 남의 계좌 조회 시도 | 소유권 검증 |
| F4 | 이미 분실 정지된 카드를 다시 일시잠금 시도 | 상태 전이 규칙(불가능한 전이 차단) |
| F5 | 존재하지 않는 계좌 조회 | 존재하지 않는 리소스 처리 |
| F6 | 이미 처리 완료된 요청을 다시 승인 시도 | 멱등성/상태 확인 |
| F7 | 승인 전 금액을 수정한 뒤 재확인·승인 | "승인 전 수정" 흐름 |

```
F1. 잔액 부족 이체 시도
  결과: success=False, error_type=InsufficientBalanceError

F2. 이미 납부한 청구서 재납부 시도
  결과: success=False, error_type=BillAlreadyPaidError, message=demo-bill-1

F3. 다른 사람이 남의 계좌 조회 시도 (소유권 검증)
  예외 발생: NotOwnerError: demo-acc-1

F4. 이미 분실정지된 카드를 다시 일시잠금하려는 시도
  결과: success=False, error_type=CardNotUsableError, message=demo-card-1

F5. 존재하지 않는 계좌 조회
  예외 발생: AccountNotFoundError: no-such-account

F6. 이미 처리된 요청을 다시 승인 시도 (멱등성/상태 확인)
  예외 발생: PendingRequestNotPendingError: req-s5

F7. 승인 전 수정(revise) 후 재확인
  최초 제안: {'from_id': 'demo-acc-2', 'to_id': 'demo-acc-1', 'amount': 100000}
  수정 후:   {'from_id': 'demo-acc-2', 'to_id': 'demo-acc-1', 'amount': 30000}, status=대기
  승인 결과: success=True
```

모든 실패가 예외를 그대로 던지지 않고(F3/F5/F6는 Orchestration의 소유권/상태 검증 단계에서,
F1/F2/F4는 `approve()`가 도메인 예외를 잡아 `ActionResult(success=False, ...)`로 구조화해)
호출한 쪽(Agent)이 항상 일관된 형태로 실패를 안내할 수 있게 되는 걸 확인했습니다.
