# langgraph-mini

LangGraph 기반 계좌·카드·청구서 관리 에이전트. Gemini가 자연어 요청을 이해해 계좌 이체,
카드 정지/재발급, 청구서 납부 같은 **잔액이나 상태를 바꾸는 작업은 항상 사용자 승인을 받은
뒤에만** 실행하고, 조회는 바로 답한다. 터미널 CLI와, 은행 앱처럼 만든 웹 화면(대시보드/계좌/
이체/카드/청구서 + 챗봇) 둘 다 같은 백엔드(agent/orchestration/account/card/billing)를
그대로 쓴다.

**실제 배포**: <https://virtual-financial-services.ai-agent-develop.cloud/chat> — 설치 없이
바로 접속해볼 수 있는 데모 서비스입니다(전부 가짜 데모 데이터·데모 계좌이고 실제 결제·개인
정보는 아닙니다).

## 요구 사항

- Python >= 3.13
- [uv](https://docs.astral.sh/uv/)
- Gemini API 키 ([Google AI Studio](https://aistudio.google.com/apikey)에서 발급)
- (웹 화면을 로컬에서 직접 띄울 때만) Docker — 로컬 Postgres/Redis용

## 실행 방법

### 1) CLI (터미널 데모)

```bash
uv sync
cp .env.example .env   # 이 파일에 GOOGLE_API_KEY 채우기
uv run langgraph-mini
```

터미널에 뜨는 `나>` 프롬프트에 자연어로 입력하면 됩니다. `exit` 또는 `quit`으로 종료.

- **데이터**: `data/*.json`에 저장됩니다. 프로그램을 껐다 켜도 계좌 잔액·카드 상태·청구서
  납부 여부·승인 대기 중이던 요청이 그대로 남아있습니다(재시작 복구).

### 2) 웹 화면(은행 스타일 UI + 챗봇)을 로컬에서 띄우기

```bash
docker compose -f docker-compose.dev.yml up -d
docker exec -i langgraph_mini-postgres-1 psql -U postgres -d postgres < src/langgraph_mini/db/schema.sql

cp .env.example .env
# .env에 GOOGLE_API_KEY 채우고, 아래 두 줄 주석 해제(docker-compose.dev.yml 기본값 그대로)
# DATABASE_URL=postgresql://postgres:devpassword@localhost:5432/postgres
# REDIS_URL=redis://localhost:6379/0

uv run uvicorn langgraph_mini.api.app:app --app-dir src --reload
```

브라우저로 <http://localhost:8000/chat> 접속. 데이터는 로컬 Postgres/Redis에 저장됩니다
(CLI의 JSON 파일과는 완전히 별도).

### 3) 그냥 실제 배포로 확인하기

설치 없이 <https://virtual-financial-services.ai-agent-develop.cloud/chat>에 접속하면 됩니다.

- **첫 실행 데모 데이터**: 이 프로젝트엔 계좌/카드/청구서를 새로 "만드는" 기능이 없어서(기존
  것을 다루는 기능만 구현했음), 저장소가 비어있으면 자동으로 만들어둡니다 — 내 계좌 2개
  (생활비 500,000원 / 저축 2,000,000원), 카드 1개(생활비 체크카드), 청구서 1개(전기요금
  45,000원), 그리고 **이체 테스트용 타인 계좌 2개**(김철수 / 이영희 — 다른 사람에게도 이체가
  되는지 확인하는 용도). 아래 요청 예시들은 전부 이 데모 데이터를 기준으로 합니다.
- **테스트**: `uv run python -m pytest` (206개 통과, 로컬 Postgres/Redis 없이). `docker
  compose -f docker-compose.dev.yml up -d`로 띄운 뒤 `TEST_DATABASE_URL`/`TEST_REDIS_URL`을
  채우고 돌리면 SQL/Redis 레포지토리 테스트 + REST API 통합 테스트까지 253개 전부 통과합니다.

## 구현한 기능

### 계좌

| 기능 | 설명 |
|---|---|
| 계좌 조회 | 잔액·별명 조회, 여러 계좌 잔액 합계 조회 |
| 계좌 별명 변경 | 같은 소유자 내에서만 별명 중복 금지 |
| 이체 | 즉시 이체 / 잔액 중 일정액만 남기고 나머지 이체(조건부) / 여러 계좌로 나눠 이체(분할). **내 계좌뿐 아니라 타인 계좌로도 이체 가능**(`to_id`엔 소유권 검증이 없음 — 실제 은행처럼 상대는 내 소유가 아니어도 됨) |
| 거래내역 조회 | 기간·금액·거래유형 필터, 최근순 정렬 |

### 카드

| 기능 | 설명 |
|---|---|
| 카드 조회 | 이름·종류(신용/체크)·상태 조회 |
| 분실 정지 | 사용가능/일시잠금 상태에서 가능 |
| 일시 잠금 / 잠금 해제 | 분실 정지와 구분됨(잠금 해제로는 분실 정지를 못 풂) |
| 재발급 신청·조회·수정·취소 | 배송지(집/회사) 지정, 이미 신청 있으면 안내, 제작 시작 전까지만 수정·취소 가능. 분실정지 상태인 카드만 재발급 신청 가능 |
| 정지 후 재발급 | 분실 정지와 재발급 신청을 이어서 처리하되 각각 따로 승인받음 |

### 청구서

| 기능 | 설명 |
|---|---|
| 미납 청구서 조회 | 납기일 빠른 순 |
| 단건 납부 | 기한이 지나도 연체료 없이 납부 가능, 이미 낸 건 재처리 안 함 |
| 일괄 납부 | 납기일 빠른 순으로 처리, 잔액 부족 건은 건너뛰고 계속 진행, 저장 실패 시 그 건부터 중단(완료/실패/미처리로 구분해 안내) |

### 대화·승인 (Orchestration + Agent)

| 기능 | 설명 |
|---|---|
| 승인·거절 | 잔액/상태를 바꾸는 요청은 전부 LangGraph의 `interrupt`/`resume`으로 사용자 확인을 거친 뒤 실행 |
| 변경 결과 저장·조회 | 승인된 변경은 저장되고, 이후 조회는 그 데이터를 그대로 반영 |
| 불완전한 요청 안내 | 정보가 부족하거나 실행할 수 없는 요청은 이유를 안내하고 되물음 |
| 추가 질문 | 대상이 여러 개면 후보를 보여주고 선택받음 |
| 승인 전 수정 | "아니, 5만 원만" 같은 수정 요청을 반영해 전체 내용을 다시 보여주고 재승인 |
| 자연어 승인·취소 | "응, 진행해"/"취소할게" 같은 자연어를 승인/거절로 해석 |
| 후속 결과 조회 | "아까 이체가 됐어?" — 이전 요청의 성공·실패·취소 여부와 처리 내용 안내 |
| 대화 대상 확인 | "그 카드 잠가줘" 같은 지시어의 대상이 불분명하면 확인, 후보 여러 개면 선택받음 |
| 재시작·장애 복구 | 프로그램이 재시작돼도 승인 대기 중이던 요청을 이어서 확인받을 수 있음(자동 실행은 안 함) |

### 웹 프론트엔드 — 은행 스타일 UI (신규)

CLI/챗봇과 완전히 같은 백엔드를 그대로 쓰는 웹 화면. React 없이 순수 HTML/JS 한 페이지
(`api/static/chat.html`)로, 모바일 폰 프레임 형태입니다.

| 화면 | 설명 |
|---|---|
| 대시보드 | 전체 자산, 계좌 카드, 청구서 알림 배너, 빠른 메뉴(이체/계좌조회/카드관리/청구서) |
| 전체계좌조회 / 계좌상세 | 계좌 목록, 거래내역(서버엔 없는 "거래 후 잔액"을 현재 잔액에서 역산해 표시) |
| 이체 | **계좌번호 직접 입력**(존재하지 않으면 에러 토스트로 안내) 또는 저장된 목록에서 선택하는 방식 토글, 금액 키패드, 확인 화면 — 내 계좌뿐 아니라 타인 계좌(김철수/이영희)로도 실제 이체됨 |
| 카드관리 | 분실신고 / 일시잠금·해제 / 재발급(도메인 규칙대로 분실정지 상태에서만 버튼 활성화) |
| 청구서 | 미납 조회, 단건/일괄 납부 |
| 챗봇 위젯 | 우측 하단 플로팅 버튼 — 기존 자연어 대화 그대로 |

대시보드/계좌/카드/청구서 화면은 REST API로 직접 Orchestration을 호출합니다(챗봇만 LLM을
거침). 화면의 "확인" 단계 자체가 사람의 승인 역할이라 별도 승인 엔드포인트는 없고, 도메인
예외는 HTTP 404/403/400 + 한글 메시지로 변환됩니다.

| 메서드 · 경로 | 설명 |
|---|---|
| `GET /api/accounts` | 내 계좌 목록 |
| `GET /api/accounts/recipients` | 이체 받는사람 후보(타인 계좌 — 닉네임만, 잔액은 비노출) |
| `GET /api/accounts/{id}/transactions` | 계좌 거래내역(본인 계좌만 조회 가능) |
| `GET /api/cards` | 카드 목록 |
| `GET /api/bills` | 미납 청구서 |
| `POST /api/transfer` | 이체 |
| `POST /api/cards/{id}/lost` `/lock` `/unlock` `/reissue` | 카드 상태 변경·재발급 신청 |
| `POST /api/bills/{id}/pay`, `POST /api/bills/pay-all` | 청구서 단건·일괄 납부 |

## 확인해 볼 요청 예시

데모 데이터(생활비 500,000원 / 저축 2,000,000원 / 생활비 체크카드 / 전기요금 45,000원 /
타인 계좌 김철수·이영희) 기준입니다. 챗봇 위젯(CLI와 동일)에서는 아래를 자연어로, 은행 UI
화면에서는 버튼·입력으로 그대로 시도해볼 수 있습니다.

**조회**
- "내 계좌 목록이랑 잔액 보여줘"
- "생활비 계좌 최근 거래내역 보여줘"
- "내 카드 상태 알려줘"
- "아직 안 낸 청구서 있어?"

**이체**
- "생활비에서 저축으로 10만원 이체해줘"
- "생활비 계좌에 50만원만 남기고 저축으로 옮겨줘" (조건부 이체)
- "생활비에서 저축으로 10만원, 김철수한테 5만원 이렇게 나눠 보내줘" (분할 이체 — 이번에 받는사람 데모 계좌가 추가돼서 실제로 여러 대상에 나눠 보낼 수 있음. 다만 이 문구로 실제 Gemini와 대화해서 확인해본 적은 아직 없음 — 코드 자체는 자동화 테스트로 검증됨)
- (웹 UI) 이체 화면에서 계좌번호에 `demo-acc-3`(김철수) 또는 `demo-acc-4`(이영희) 입력 → 타인 계좌로 실제 이체되는지 확인

**카드**
- "생활비 카드 잃어버렸어. 정지해줘"
- "생활비 카드를 집에 둔 것 같아. 잠깐 잠가줘"
- "생활비 카드 찾았어. 잠금 풀어줘"
- "잃어버린 생활비 카드를 집으로 재발급받고 싶어"
- "카드 재발급 신청 상태 알려줘"
- "재발급 카드 배송지를 회사로 바꿔줘"

**청구서**
- "생활비 계좌에서 전기요금 납부해줘"
- "생활비 계좌에서 미납 청구서 전부 납부해줘"

**대화 흐름 (승인/거절/수정)**
- 위 요청 중 하나를 보낸 뒤 → "응 진행해" / "아니 취소할게" / "아니, 절반만"
- "아까 이체가 됐어?" (직전 요청 결과 재확인)
- "그 카드 잠가줘" (바로 앞 대화에서 언급한 카드를 대명사로 지칭)

**의도한 실패/되묻기 상황**
- "이체해줘" (계좌·금액 등 정보 부족 — 되물어야 함)
- "생활비에서 저축으로 -1만 원 옮겨줘" (실행 불가능한 값)
- (웹 UI) 이체 화면에서 존재하지 않는 계좌번호(예: `999999`) 입력 → 에러 토스트로 안내되는지 확인

## 구현 기능 동작 확인 결과

실제 `https://virtual-financial-services.ai-agent-develop.cloud/chat`에 실제 Gemini API로
배포해서 조회·이체 제안·자연어 승인·잔액 반영까지 프로덕션 HTTPS로 직접 확인했습니다(계좌
잔액이 실제로 바뀌는 것까지 Postgres에서 직접 조회해 검증). 이 과정에서 실제 모델 응답이
가끔 일반 문자열이 아니라 다중 파트 리스트로 오는 문제를 발견해 수정하기도 했습니다(아래
"실행 중 발견한 버그" — `최종설계자료/폴더_구조.md` 참고). 이 문서의 성공/실패 시나리오는 그
아래 실행 로직(Orchestration → 도메인 서비스)을 CLI와 동일한 조립 방식으로 직접 호출해
재현한 것이고, `tests/`의 자동화 테스트 253개(로컬 Postgres/Redis 포함)로도 반복 검증됩니다.

### 성공 시나리오

```
S1. 계좌 목록 조회
  demo-acc-1 | 생활비 | 잔액 500,000원
  demo-acc-2 | 저축 | 잔액 2,000,000원

S2. 카드 목록 조회
  demo-card-1 | 생활비 체크카드 | 체크 | 상태 사용가능

S3. 미납 청구서 조회
  demo-bill-1 | 전기요금 | 45,000원 | 납기 2026-10-08

S4. 정상 이체: 생활비 -> 저축 50,000원 (propose -> approve)
  이체 전: 생활비=500,000 저축=2,000,000
  propose 결과: status=대기
  approve 결과: success=True
  이체 후: 생활비=450,000 저축=2,050,000

S5. 카드 분실 정지 (propose -> approve)
  approve 결과: success=True, 카드 상태=분실정지

S6. 청구서 납부 (propose -> approve)
  approve 결과: success=True
  거래내역: 청구서납부 45,000원

S7. 승인 전 거절(reject) — 카드 일시 잠금 제안 후 거절
  reject 결과: status=거절됨
  (demo-card-1은 S5에서 이미 분실정지 상태라 이 제안이 실행됐어도 실패했을 것 —
   거절이 도메인 호출 자체를 안 하는지 확인하는 용도)
```

### 직접 선정한 실패 시나리오

| # | 시나리오 | 확인 목적 |
|---|---|---|
| F1 | 잔액보다 큰 금액 이체 시도 | 잔액 부족을 구조화된 실패로 반환(예외가 그대로 안 튐) |
| F2 | 이미 납부한 청구서 재납부 시도 | 중복 처리 방지 |
| F3 | 다른 사용자가 남의 계좌 조회 시도 | 소유권 검증 |

### 웹/REST API 동작 확인 (통합 테스트 + 실제 배포)

`tests/test_api_app.py`가 실제 `TestClient`로 앱 전체(lifespan 포함)를 띄워 REST 엔드포인트를

  `AccountNotFoundError`인데 발생 시점이 달라서(전자는 승인 전 소유권 검증 단계, 후자는
